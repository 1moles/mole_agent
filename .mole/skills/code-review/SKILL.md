# 代码检视（Mole / kernel 项目）

目标：在合入前发现会出问题的改动。宁可少报，不要凑数；每条结论都要有代码依据。
全程只读：不修改、不格式化、不安装依赖。用户明确要求修复时，再逐条确认后动手。

## 1. 确定检视范围

| 用户的说法 | 取改动的方式 |
|---|---|
| 没说 / 「我改的」「未提交的」 | `git_changes` |
| 「暂存的」「add 过的」 | `git_changes`，`staged=true` |
| 某个提交 | `bash`：`git show --stat <sha>`，再 `git show <sha>` |
| 分支、「和 main 比」 | `bash`：`git diff <base>...HEAD --stat`，再 `git diff <base>...HEAD` |
| 指定文件或目录 | 直接 `read_file`，按整份代码检视 |

范围不明确（比如分不清要对比哪个分支）时用 `ask_user` 问，不要猜。
新增的未跟踪文件（status 里的 `??`）不在 diff 里，要单独 `read_file`。

## 2. 理解改动，再下结论

1. 先看 `--stat`：改了哪些模块、规模多大。超过约 800 行时按模块分批看，每批给出阶段结论。
2. 每个改动文件都 `read_file` 看完整上下文，不能只看 diff 片段。
3. 用 `grep` 找被改函数、类、配置项的调用方和测试，确认影响面。
4. 用 `skill_tool` 读取本技能的 `references/mole-conventions.md`（参数 `relative_file_path`），
   对照项目约定检查。
5. 细项清单在 `references/checklist.md`，改动较大或涉及安全、并发、配置时逐项过一遍。

## 3. 检查顺序（按优先级）

1. **正确性**：逻辑错误、边界条件（空值 / None / 超长 / 编码）、异常路径、async 用法
   （漏 await、在事件循环里做阻塞 IO、吞掉 CancelledError）、资源释放。
2. **安全**：命令注入、路径越界、密钥泄露（日志、审计、异常信息）、放宽沙箱或确认策略、
   新的 bash 拒绝规则有没有漏拦或误拦。
3. **兼容性**：与 PyPI 发布版 openjiuwen（0.1.18.x）是否兼容；是否依赖 SDK 私有属性；
   `.env`、`models.toml`、`state.json`、命令行参数、斜杠命令的旧用法是否还能用。
4. **测试**：新行为有没有测试；测试是否隔离（不联网、不读开发者真实配置）；断言是否真的验证了行为。
5. **可维护性**：与现有模块职责和写法是否一致、重复实现、命名、注释是否解释了「为什么」。
6. **性能**：循环里的 IO、整文件读入大文件、无界增长的缓存或列表。

AI 生成的代码要额外核对：调用的 SDK 接口和参数是否真实存在（`grep` 或看已安装的
openjiuwen 源码确认）、是否用宽泛的 `try/except` 吞掉了错误、测试是否只在断言 mock 本身。

## 4. 验证（可选）

可以提议跑下面的命令作为证据（`bash` 需要用户确认）；不跑也要在结论里说明未验证：

```bash
python -m compileall -q mole_agent tests
pytest -q
```

## 5. 输出格式

```
## 检视范围
<来源（未提交/暂存/提交 xxx/分支 a...b）> · <N 个文件> · <+增 / -删 行>

## 问题
### [阻塞] <一句话标题>
- 位置：`mole_agent/cli.py:123`
- 问题：<哪里错了>
- 影响：<什么情况下会出什么事>
- 建议：<怎么改；必要时附修改后的代码片段>

### [建议] ...
### [可选] ...

## 未能确认
- <需要作者补充信息或运行验证才能判断的点>

## 结论
建议合入 / 修改后合入 / 不建议合入 —— <一句话理由>
```

级别：
- **阻塞**：会导致错误行为、安全问题、数据丢失，或破坏已有接口 / 配置兼容性。有阻塞项时结论不能是「建议合入」。
- **建议**：不影响正确性，但会带来维护成本或潜在风险，应在本次或下次修改。
- **可选**：风格、可读性等小问题，最多列 5 条。

没有发现问题的级别直接省略。「未能确认」没有内容也省略。
