初始化或改善当前项目的规则文件，供后续编码会话使用。

将完整的新版本写入下面指定的“草稿输出文件”，不要直接修改目标规则文件或项目代码，不运行 git add/commit。Mole 会在本轮正常结束后检查并写回草稿，然后刷新当前会话的规则。不要声称已经写回或加载，实际结果由 Mole 报告。

## 调查与证据

- 先读取已有目标规则文件（若存在），保留有效的人工约定。优先分析 README、依赖与工作区配置、构建/测试/lint/格式化配置、CI 和已有规范；有必要时再读取少量关键源码，确认真实入口和模块职责。
- 已有人工规范说明“应该怎样做”，源码、配置和脚本说明“当前怎样实现”。实现与规范冲突时，不擅自用实现替换规范；重要冲突应明确说明，必要时询问用户。
- 保持原约定的适用范围和语气，不把“建议”“需要兼容”“当前验证过”改写成“必须”“只允许”“只兼容”。不要从依赖下限推断独占版本或已验证的兼容范围。
- 对照当前模块及相关未提交改动，避免遗漏新增的重要能力；只读检查，不修改或暂存这些改动。规划文档只能作为线索，未经代码确认的计划不能写成已实现功能。不要将本机路径、系统版本或临时状态当作项目通用要求。
- 按重要性补读，避免遍历整个仓库。已有证据足以支持必要的项目约定时停止调查；不足以确定且确实重要的团队约定可询问用户，仓库能够回答的问题自行查明。

## 内容与篇幅

- 使用简洁 Markdown，遵循当前会话语言及项目现有文档习惯。
- 只记录会改变后续 Agent 工作方式、容易遗漏或猜错的项目特有信息：准确的开发命令（尤其单个测试和局部检查）、重要模块职责、特殊约定、开发约束和有依据的注意事项。
- 命令、脚本名和测试用例名必须有实际依据；优先给可直接执行的真实示例，必要的占位符须明确标注。初始化配置的命令仅用于文件不存在时，不能指导覆盖已有配置。不要为了核对示例而执行有副作用或需要外部服务的命令；未运行的检查不得标为已验证。
- 模块职责与依赖关系分开描述；只有核对实际 import 或调用关系后才能描述依赖方向，不能把目录排列当作分层规则。
- 已有详细文档保留关键约束并引用仓库相对路径，避免大段复述。保留有效人工约定，以增量改善为主；不要为了压缩篇幅删除必要约束。
- 排除通用编程建议、冗长目录树、完整代码和凭据。不要读取 .env 或凭据文件来获取秘密。
- 小型项目优先控制在 2000–4000 字符；必要的项目特有约束可以超出，但完整草稿不得超过 20000 字符。不为凑章节补充内容。

## 写入前自查

- 核对命令与引用路径真实存在、版本表述有依据、规则强度未被放大；检查是否遗漏当前实现的重要能力、是否与已有规范冲突、是否重复详细文档。能查明的问题先核实；无法确认的推断删除，确实重要的不确定性明确说明。
- 写草稿前重新读取已有目标文件，发现外部修改时停止并说明。
- 如果已有文件无需改进，将原内容原样写入草稿；结束时概述本次检查与建议变化。
